## Findings

### W-01 · P1 · CI on `main` is red: date-dependent backup test [Run]
`web/tests/cross-platform-backup.test.ts:61` expects `streak === 8` after importing `androidPlaintext`. The fixture's activity log ends on **2026-10-17**. On import, `mergeStats` recomputes the streak with `calculateStreakFromDates(activeDates)` (`web/src/lib/db/backup.ts:868`), and that call uses the real clock. From 2026-10-19 onward the last active day is more than a day old, so the streak correctly decays to 0 and the test fails. The production code is correct. The bug is in the test.
**Fix:** inject `today` into the import path (or use `vi.useFakeTimers()` / `vi.setSystemTime("2026-10-17T12:00:00Z")` in this test).
Also, the fixture's `lastActivityTimestamp` is `1729123200000`, which is 2024-10-17, two years before its own activity dates. That looks like a typo.

### W-02 · P1 · Offline PWA is permanently disabled after the first logout or session expiry [Static]
`web/public/sw.js` stores a persistent `loggedOut: true` flag in IndexedDB (`deutschflow-session`) when:
- the user logs out (`PURGE_*`/`LOGOUT` message), or
- any navigation comes back as `/login`. This also happens when the 30-day cookie simply expires.

The flag is cleared only by a `SESSION_ESTABLISHED` message (`sw.js:229`) or by line 299. Nothing in `web/src` sends `SESSION_ESTABLISHED`, and nothing calls `setPersistentSessionLoggedOut(false)`. Line 299 can never run while the flag is set, because lines 288–295 return early when `isPersistentSessionLoggedOut()` is true. After the first logout or expiry, every later navigation:
- is never written to cache, and
- gets `503 Offline - Content unavailable` when offline (`sw.js:326`).

The flag lives in IndexedDB, so it survives new service-worker versions and deploys. Every long-term user eventually loses offline boot, which the README advertises.
**Fix:** after a successful login, post `SESSION_ESTABLISHED` to the controller (login page) and/or clear the flag window-side. Alternatively, treat a 200 non-redirected navigation as proof of a live session *before* the logged-out check. Add a Playwright test: log out → log in → go offline → reload.

### W-03 · P2 · Web streak never decays (parity gap with Android F-09) [Static]
`DashboardContent.tsx:19` renders `userStats.streak` as stored. Android fixed the same bug in #45 with `UserStatsEntity.currentStreak()`, which returns 0 when more than one civil day has passed. The web never got the fix. A user who stopped two weeks ago still sees their old streak until their next review resets it to 1.
**Fix:** port `currentStreak()` to `repository.ts` and use it in the dashboard. Add the case to the shared contract fixture so the two platforms can't drift again.

### A-01 · P2 · Android study progress reaches 100% with "Again" cards still queued [Static]
`StudyScreen.kt:238` computes `totalInSession = max(initialSessionSize, studyList.size)`. When a card is rated **Again**, `sessionReviewedCount` goes up and the card is re-queued (`StudyViewModel.kt:238,244`), so the true total grows. Example with 3 cards and one Again: after 3 ratings, the counter shows **3 / 3** and the bar shows **100%** with one card left. The web computes `max(initialSessionSize, reviewed + remaining)` (`study/page.tsx:257`) and gets this right (3 / 4, 75%).
**Fix:** `val totalInSession = maxOf(initialSessionSize, sessionReviewedCount + studyList.size)`.

### W-04 · P2 · Self-hosted login throttle is one global bucket [Static]
Off Vercel, `extractCallerKey` returns `"unknown"` for every request (`api/login/route.ts:307`). This is deliberate, so clients can't spoof the key. The consequences:
1. One attacker's failed guesses put **every** user into the 30 s cooldown.
2. Any legitimate successful login calls `recordThrottleSuccess("unknown")` and **resets the attacker's counter**. The brute-force brake falls back to the 3 free attempts every time someone logs in.

**Fix:** add an opt-in `TRUSTED_PROXY_HEADER` (or similar) for self-hosted deployments behind a known proxy, and document the limitation in `docs/SECURITY.md` / `.env.example`.

### W-05 · P3 · Rate limit is weak against a low-entropy `SITE_PASSWORD` [Static]
The cooldown is capped at 30 s and the window is 15 min, so one key gets about 2,880 guesses a day indefinitely. Without Upstash, every serverless instance also has its own counter. That is fine for a high-entropy password and not fine for a memorable one. Nothing enforces or warns about password strength.
**Fix:** require a minimum length, as `SESSION_SECRET` already does, or at least warn at startup.

### W-06 · P3 · Logout does not protect on-device data (expectation gap) [Static]
The access gate and the logout cache purge protect only the HTML shell. `/_next/*` chunks are public, and all user data (vocabulary, transcripts, roleplay, the encrypted Groq key) stays in IndexedDB after logout. On a shared device, the next person who logs in with the shared site password sees the previous user's library. The gate is a site-access control, not a per-user one. This is worth stating plainly in Settings or SECURITY.md, or offering a "log out and wipe local data" option.

### X-01 · P3 · Reasoning tokens can truncate AI output (still open, F-12) [Static]
Both clients send `max_completion_tokens: 1024` (512 for roleplay) to `openai/gpt-oss-120b` and don't set `reasoning_effort`. On gpt-oss models, reasoning tokens count against that budget. A long input (up to 4,000 chars) can use up the budget before any JSON is produced, and the user then sees the "cut off" message. Not verified against the live API.
**Fix:** set `reasoning_effort: "low"` on the structured-JSON calls, or raise the cap. Check with a live key.

### W-07 · P3 · A request timeout is reported as "Request cancelled" [Static]
`post()` in `web/src/lib/ai/groq.ts` aborts its own controller after 30 s. That throws an `AbortError`, and every caller maps an `AbortError` to `ai.cancelled`. A slow network looks like something the user did. **Fix:** tell the internal timeout apart from `externalSignal.aborted` and map the timeout to the no-response or timeout message.

### W-08 · P3 · `GROQ_MODEL` override is dead on the client [Static]
`getActiveGroqModel()` reads `process.env.GROQ_MODEL`, but it runs in browser code, where Next inlines only `NEXT_PUBLIC_*` variables. The override never applies. Either rename it to `NEXT_PUBLIC_GROQ_MODEL` or remove it.

### X-02 · P3 · New SRS interval badges are English-only [Static]
`formatInterval` / `formatSrsInterval` (added in `f0b6a2e`) hardcode `"< 10m"`, `"d"`, `"mo"`, `"y"`. German users see English units, even though the commit claims full localization parity. `audit_repo.py` can't catch this because the strings aren't in the resource files. **Fix:** move the units into `strings.xml` / `i18n.ts` (e.g. `T`, `Mon.`, `J.` for German).

### X-03 · P4 · Hygiene and tech debt
- `android:largeHeap="true"` in the manifest. Nothing in the app needs it, and it hides memory leaks. Remove it unless a measured case exists. **Fixed:** removed. Backup import was the one measured case: `importFromStream` buffered the whole file in a `StringBuilder` before checking the 50 MiB cap, so the API 31 "one byte over" test hit `OutOfMemoryError`. `BackupManager.readBackupText` now reads into a pre-sized byte buffer, rejects oversize plaintext from the byte count before any String exists, and builds the String once. `BackupStreamReadTest` covers the size-check order.
- `hs_err_pid19960.log` (95 KB) and `replay_pid19960.log` (14 MB) in the repo root are left over from a JVM out-of-memory crash on 11 Oct. They're git-ignored, so not committed, but they can be deleted. `org.gradle.jvmargs=-Xmx2048m` plus Kotlin/KSP daemons on this machine are the likely cause.
- `web/src/lib/auth/throttle.ts` (757 lines) has a whole "synchronous API" and `recordThrottleFailure` / `getThrottleDelay` that production code doesn't use. Only tests call them. Trimming them would halve the file.
- The service worker and `lib/auth/logout.ts` duplicate `APP_SHELL_ROUTES`, `isProtectedAppRoute` and the session-DB code by hand. They will drift.
- Dependencies: minor and patch updates are available (Next 16.4.2, React 19.3.1, Dexie 4.4.6, Vitest 5.0.5). Dependabot covers these.
