## A. Executive summary

**Release recommendation: not ready for a production Play release.** The codebase is above average for its size. Error handling is deliberate, the migrations are tested, the API-key storage is sound, speech recognition is on-device only, and AI output is validated. Four problems still block a defensible release:

1. **The daily-word notification never reaches Android 13+ users (F-01, P1).** `POST_NOTIFICATIONS` is declared but never requested anywhere in the app. With `targetSdk = 37`, a fresh install on API 33+ has notifications off, the worker posts nothing, and the Settings "test" button only reports that notifications are off. The KDoc in `MainActivity` says Settings requests the permission. It does not.
2. **A flashcard review can silently revert a library edit (F-02, P1).** `submitReview` writes back the full row snapshot taken when the deck loaded. Edit a word in Library during an open session, rate that card, and the edit is gone.
3. **Merging vocabulary loses learning data (F-03, P1).** Renaming a word onto an existing one discards the renamed card's SRS state, whichever card was further along, and orphans its review history. Delete followed by Undo also orphans review history.
4. **Privacy and Play compliance gaps (F-11, F-12).** There is no in-app privacy policy, and the app requests `RECORD_AUDIO` and sends user text to a third-party AI. There is no way to delete the stored API key. Speech transcripts and roleplay conversations are included in Android cloud backup and device transfer. The Data Safety answers have to reflect all of this.

**Strengths (verified in code):** API key under Android-Keystore AES-GCM with no plaintext fallback, excluded from backup. Speech recognition is forced on-device (`createOnDeviceSpeechRecognizer`, no cloud fallback). The PendingIntent is immutable and explicit. Traffic is HTTPS-only. Prompts separate system and user roles, and the parsers bound and whitelist model output. Room schemas are exported, there is a migration for every version, migration tests exist, and release builds have no destructive fallback. The review, XP and review-event writes share one transaction. `launchGuarded` keeps background failures from crashing the app. R8 strips debug and verbose logs. CI actions are pinned by SHA with least-privilege permissions, and Dependabot is enabled.

**Major risks:** learning-data integrity around edits and merges (F-02, F-03, F-08), AI cancellation and cost behaviour (F-05, F-13), and the privacy disclosures (F-11, F-12).

## B. Architecture assessment

### B.1 Map

```
MainActivity (single Activity, Compose) ──► MainNavigation (NavHost, 5 routes)
  ├─ transcript  → TranscriptScreen ── TranscriptViewModel ─┬─ SpeechRecognizerHelper (per-VM, on-device only)
  │                                                          ├─ VocabularyProcessor → GroqHelper (HTTPS, Groq)
  │                                                          ├─ TranscriptDao, VocabularyDao, PreferenceManager
  │                                                          └─ WidgetUpdater, TTSHelper(@Singleton)
  ├─ vocabulary  → LibraryScreen ─┬─ VocabularyScreen/VocabularyDetailScreen ── VocabularyViewModel ── VocabularyDao
  │                               └─ HistoryScreen ── HistoryViewModel ── TranscriptDao
  ├─ study       → StudyScreen ─┬─ DashboardScreen ── DashboardViewModel ── ActivityDao, UserStatsDao, VocabularyDao
  │                             └─ flashcards ── StudyViewModel ── AppDatabase.withTransaction{VocabularyDao, ReviewEventDao, UserStatsDao, ActivityDao}, SRSEngine
  ├─ practice    → PracticeScreen ─┬─ Shadowing ── PracticeViewModel ── SpeechRecognizerHelper, VocabularyDao
  │                                └─ RoleplayScreen ── RoleplayViewModel ── SpeechRecognizerHelper, GroqHelper, RoleplayDao
  └─ settings    → SettingsScreen ── SettingsViewModel ── PreferenceManager(DataStore + KeystoreCipher), all DAOs, DailyWordNotification
MainApp.onCreate ── DailyWordWorker.schedule / rescheduleIfZoneChanged (WorkManager periodic, 09:00)
DailyWordWorker ── WorkerEntryPoint ── DailyWordNotification, WidgetUpdater
WordWidget (Glance) ── WidgetEntryPoint ── DailyWord ── VocabularyDao
Room v16: vocabulary, transcripts, user_stats, activity_log, roleplay_messages, review_events (no foreign keys)
```

- **DI lifetimes:** `AppDatabase`, the settings `DataStore`, `PreferenceManager`, `KeystoreCipher`, `TTSHelper`, `DailyWord`, `DailyWordNotification`, `WidgetUpdater`, `SRSEngine` and `VocabularyProcessor` are `@Singleton`. `SpeechRecognizerHelper` and `GroqHelper` are unscoped. Each speech-using ViewModel owns its own recognizer and destroys it in `onCleared`, which is correct.
- **Dependencies:** AGP 9.4.0, Kotlin 2.4.20, KSP 2.3.11, Hilt 2.60.1, Room 2.8.4, Compose BOM 2026.08.00, WorkManager 2.11.2, Glance 1.1.1, DataStore 1.2.1. minSdk 31, compile and target SDK 37, Java/JVM 11. There are no third-party networking, analytics or crash-reporting SDKs. I did not check versions against a registry (no network check was done); Dependabot covers Gradle weekly.

### B.2 Maintainability concerns (concrete only)

1. **No repository layer.** ViewModels call DAOs directly, and rules about data integrity are spread across them: the merge rules live in `VocabularyDao.save`, the review and XP rules in `StudyViewModel`, and undo in `VocabularyViewModel`. That spread is why F-02 and F-03 exist. Each caller handles only part of the "card identity" lifecycle. One `VocabularyRepository` that owns save, rename, merge, delete, restore and review, each in a single transaction, would fix the class of bug rather than each instance. This is the one abstraction I recommend.
2. **`review_events` has no relationship to `vocabulary`** (no foreign key and no reassignment). Every code path that changes a card's identity has to maintain it by hand, and none of them do (F-03).
3. **Composable-scoped writes.** Transcript Save and Undo run in `rememberCoroutineScope`, outside the `launchGuarded` discipline the rest of the app uses (F-08).
4. **Comments contradict the code in two places,** and both hide defects: `MainActivity.kt:26-29` (F-01), and `RoleplayViewModel.kt:317-320`, which says "the header renders the localized resource" when it renders the English catalogue title (F-17).

## C. Findings register

The severities are my judgement: P0 critical, P1 high, P2 medium, P3 low. Confidence reflects the evidence label.

### F-01 — P1 — The notification permission is never requested, so the daily word never reaches Android 13+ users *(Prior #2: CONFIRMED)*
- **Evidence [Static]:** `AndroidManifest.xml:7` declares `POST_NOTIFICATIONS`. A repo-wide search finds no runtime request for it. The only `RequestPermission()` launchers are for `RECORD_AUDIO` (`TranscriptScreen.kt:106`, `PracticeScreen.kt:119`). `DailyWordNotification.showNotification` (`DailyWordNotification.kt:53-55`) returns `message_notifications_off` when the permission is missing. `SettingsScreen.kt:393-396` calls `viewModel.testNotification()` with no permission request. `MainActivity.kt:26-29` claims "Settings requests POST_NOTIFICATIONS", which is false.
- **Repro:** Fresh install on API 33+. Never open system settings. Wait until 09:00, or tap Settings → Test notification. Expected: a permission prompt, then a notification. Actual: nothing at 09:00, and the test button shows "Notifications are turned off. Enable them… in system settings."
- **User impact:** The retention feature does nothing by default on every supported device with API 33 or higher. The daily `DailyWordWorker` runs and quietly does nothing.
- **Fix:** Request `POST_NOTIFICATIONS` in context, from a Settings "Daily word reminder" control or the test button. After one denial, deep-link to `Settings.ACTION_APP_NOTIFICATION_SETTINGS`. Correct the KDoc. Patch in §Phase 12.
- **Regression tests:** A Compose UI test on API 33+ with the permission revoked (`adb shell pm revoke`) asserting the system dialog launches, using UiAutomator. A ViewModel test asserting the permission-denied message is distinct from "library empty".
- **Confidence:** High.

### F-02 — P1 — A flashcard review writes a stale full-row snapshot, reverting library edits and banking XP for deleted words
- **Evidence [Static]:** The deck is loaded once, as full `VocabularyEntity` snapshots (`StudyViewModel.kt:113-128`). It is deliberately not reloaded on a tab switch (`ensureSessionStarted`, `:107-111`). `submitReview` takes `card` from that snapshot (`:174`), computes the new schedule from it, and calls `vocabularyDao.updateVocabulary(updatedPersisted)` (`:192`). Room's `@Update` writes every column, including `germanText`, `germanTextKey`, `englishTranslation`, `article` and the rest. Nothing re-reads the row inside the transaction.
- **Repro:** Study → Flashcards with a word "Hnud" in the deck. Switch to Library and edit it to "Haus" / "house". Return to Flashcards; the deck is not reshuffled. Rate the card Good. Expected: the schedule updates and the edit survives. Actual: the row goes back to "Hnud" with the old translation.
  - **Variant (deleted word):** Delete the word in Library, then rate it in Study. The `@Update` matches no row, but the transaction still inserts a `review_events` row for a deleted id and awards 10 XP. XP is farmed and history is orphaned.
  - **Variant (rename-merge):** If the edit renamed the word onto an existing one (the row is deleted by F-03's path), the same as the deleted variant applies.
- **User impact:** User corrections are lost silently. XP and streak inflate. This mirrors the web P1 in `docs/AUDIT_2026-09-16.md` §2, which was never carried over to Android.
- **Fix:** Inside the transaction, re-read the row by id. If it is gone, drop the card from the deck and write nothing. Otherwise compute the schedule from the fresh row and run a targeted `UPDATE` of the SRS columns only. No schema migration is needed. Patch in §Phase 12.
- **Regression tests (instrumented, in-memory Room):** `reviewAfterLibraryEditKeepsTheEdit`, and `reviewOfADeletedCardWritesNoEventAndNoXp`.
- **Confidence:** High.

### F-03 — P1 — Vocabulary merge discards SRS progress and orphans review history; delete and Undo orphan it too *(Prior #1: CONFIRMED)*
- **Evidence [Static]:**
  - The rename-collision branch in `VocabularyDao.save` (`VocabularyDao.kt:96-99`) runs `deleteById(vocabulary.id)` and then `updateVocabulary(existing.mergedWith(vocabulary, now))`. `VocabularyEntity.mergedWith` (`VocabularyEntity.kt:118-122`) always keeps the existing row's `nextReview`, `interval`, `easeFactor` and `reviewCount`.
  - The renamed card's schedule is therefore discarded even when it is further along. The SQL migrations `MIGRATION_12_13` and `MIGRATION_14_15` explicitly keep "the furthest-along SRS state in the group". The runtime rule contradicts the migration rule.
  - `review_events.vocabularyId` for the deleted id is never reassigned. `ReviewEventEntity` has no foreign key (`ReviewEventEntity.kt:10-18`, schema `16.json`).
  - `VocabularyViewModel.restoreVocabulary` (`:151-156`) re-saves with `copy(id = 0)`. Because the table is `AUTOINCREMENT`, the restored word always gets a new id, so its whole review history stays attached to the dead id.
  - `deleteVocabulary` never removes events, so orphans accumulate permanently.
- **Repro:** Card A, "Übung", has reviewCount 8 and interval 120. Card B, "Ubung" (a typo), has reviewCount 0. Edit A's text to "Ubung". Expected: the merged card keeps 8/120 and A's review events. Actual: the survivor is B with 0/0. A's events point to a deleted id.
- **User impact:** Months of scheduling can be lost through a single edit. The history table becomes unreliable for future analytics or export, though it is currently write-only except for `latestReviewTimestamp`. Existing tests do not cover this: `VocabularyDaoTest.renamingAWordOntoAnExistingOneFoldsThemTogether` asserts text fields only.
- **Fix:** In the merge branch, take the furthest-along schedule as a set, using the same ordering as the migrations (reviewCount, then interval), and run `UPDATE review_events SET vocabularyId = :survivor WHERE vocabularyId = :loser` in the same transaction. Restore must preserve the original id: add a transactional `VocabularyDao.restore(entity)` that inserts with the original id when the key is free and otherwise merges and reassigns. No schema migration is needed. Adding a foreign key later would need a table rebuild, and `CASCADE` would destroy Undo, so it is not recommended now. Patch in §Phase 12.
- **Regression tests (instrumented):** `renameOntoExistingKeepsFurthestScheduleAndReassignsEvents`, `deleteThenUndoKeepsIdAndHistory`, and `renameOntoFreeNameKeepsIdAndEvents`.
- **Confidence:** High.

### F-04 — P2 — Flashcard Skip races review submission *(Prior #3: CONFIRMED)*
- **Evidence [Static]:** The rating buttons are disabled while `isSubmitting` (`StudyScreen.kt:417`). The Skip `TextButton` (`StudyScreen.kt:458-461`) is not, and `skipCard` (`StudyViewModel.kt:268-274`) does not check `_isSubmitting`. `submitReview` captures `index` at tap time, removes `currentList[index]`, and leaves `_currentIndex` alone unless it is out of range (`:210-232`).
- **Repro:** Deck [A,B,C], index 0. Tap Good, then tap Skip while the transaction runs. Skip moves the index to 1 (B is shown). After the write the list is [B,C] and the index is still 1, so C is shown.
- **User impact:** The card on screen changes under the user, and B is skipped without the user choosing to. The card is not lost; it comes back on wrap. A flip during the window shows B's answer, then the card silently changes.
- **Fix:** Guard `skipCard` with `if (_isSubmitting.value) return` and set `enabled = !isSubmitting` on Skip. After the write, set `_currentIndex` to the new position of the card that was displayed (by id), not the stale index.
- **Regression test:** A ViewModel test that holds the transaction open (a test `AppDatabase` with a gated query executor), calls `skipCard()`, and asserts the displayed card id is unchanged after completion.
- **Confidence:** High.

### F-05 — P2 — Cancelling an AI request does not abort the network call *(Prior #8: CONFIRMED)*
- **Evidence [Static, semantics]:** `GroqHelper.post` (`GroqHelper.kt:164-166`) registers `coroutineContext[Job]?.invokeOnCompletion { connection.disconnect() }`. The public `invokeOnCompletion` fires when the job *completes*, not when it starts *cancelling*. The job here belongs to `withContext(Dispatchers.IO)`, and it cannot complete while its body is blocked in `HttpURLConnection` I/O (`outputStream`, `responseCode`, `read`). The handler therefore runs only after the blocking call returns: on a response, or after `connectTimeout` plus `readTimeout` (30 s each, and per read).
- **Repro (unit, proposed):** Point the client at a local `ServerSocket` that accepts and never answers. Start a request, cancel the job after 100 ms, and measure `join()`. Prediction: about 30 s instead of under 1 s.
- **User impact:** `TranscriptViewModel.interrogateWord` cancels superseded requests (`:364`), and leaving a screen cancels `viewModelScope`. Neither actually stops the request. Each keeps a socket and an IO thread for up to about 60 s and still uses the user's Groq quota. `onCleared` teardown is delayed. There is no data corruption, because results are discarded.
- **Fix:** Replace the completion handler with a child watchdog (`launch { try { awaitCancellation() } finally { connection.disconnect() } }`) inside `coroutineScope`. That watchdog fires on cancellation. Make the endpoint injectable so it can be tested. Patch in §Phase 12.
- **Confidence:** High on the semantics. I did not measure the timing (no build).

### F-06 — P2 — The Roleplay microphone never requests `RECORD_AUDIO`
- **Evidence [Static]:** `RoleplayScreen.kt:308` calls `viewModel.startListening()` directly. There is no permission check or launcher; compare `TranscriptScreen.kt:148-153` and `PracticeScreen.kt:119-127`. `RoleplayViewModel` has no `onPermissionDenied`.
- **Repro:** Fresh install → Practice → Roleplay tab → tap the mic. Expected: a permission dialog. Actual: the recognizer fails, and the user sees a speech error banner from `ERROR_INSUFFICIENT_PERMISSIONS`, or `speech_start_failed` if `startListening` throws. There is no prompt and no "Open settings" action.
- **Fix:** Use the same launcher pattern as Transcript, plus `onPermissionDenied()` routed to `speechRecognizerHelper.reportPermissionDenied()`.
- **Test:** A Compose UI test with the permission revoked, asserting the dialog is requested.
- **Confidence:** High for the missing request. The exact error text needs a device.

### F-07 — P2 — Transcript Save runs in the composition scope: a DB error crashes the app, and leaving mid-save cancels the write
- **Evidence [Static]:** `TranscriptScreen.kt:162-168` and `:179-186` call `scope.launch { viewModel.saveToVocabulary(...) }` and `saveWordDetails(...)` from `rememberCoroutineScope()`. That scope has no exception handler, so any exception from `vocabularyDao.save` (`SQLiteFullException`, a corrupt DB) reaches the thread's default handler, and the process dies. `launchGuarded` (`LaunchGuarded.kt`) exists to prevent exactly this. The scope is also cancelled when the screen leaves composition, which cancels the Room transaction (it rolls back) without telling the user. The Library undo snackbar has the same scope problem (`VocabularyScreen.kt:107-113`): leaving the screen inside the snackbar window removes the Undo action.
- **Fix:** Move these writes into the ViewModel (`launchGuarded` with an error state and a one-shot "saved" event), and keep only the snackbar in the UI.
- **Test:** A ViewModel test with a DAO that throws, asserting the error state is set and nothing crashes.
- **Confidence:** High.

### F-08 — P2 — German homographs are conflated, and the AI article "none" overwrites real articles on merge
- **Evidence [Static]:**
  - `germanKey` (`VocabularyEntity.kt:23-29`) lowercases everything, so *Essen* (das, food) and *essen* (to eat), *Leben/leben*, *Morgen/morgen* and *Arm/arm* share a key and can never coexist. The second save merges into the first.
  - `GroqHelper.normalizeArticle` returns `"none"` for non-nouns. `TranscriptViewModel.saveWordDetails` stores it as is (`:430`). `mergedWith` keeps `incoming.article.ifBlank { article }` (`VocabularyEntity.kt:111`). `"none"` is not blank, so interrogating the verb *essen* after saving the noun *Essen* replaces `article = "das"` with `"none"`, and the English meaning becomes "to eat".
- **User impact:** Saved grammar information is silently destroyed. This is a correctness issue specific to German learners.
- **Fix (no migration):** Normalise `"none"` to `""` when saving, and treat `"none"` as blank in `mergedWith`. **The homograph question is a product decision.** Options are a case-sensitive key for noun-capitalised entries, or a part-of-speech column. Either one changes the unique key and **requires a migration** with a re-keying pass like `MIGRATION_14_15`.
- **Tests:** A unit test in `VocabularyMergeTest` for `"none"` not overwriting `"der"`. An instrumented test for the chosen homograph policy.
- **Confidence:** High.

### F-09 — P2 — The displayed streak never decays
- **Evidence [Static]:** `DashboardScreen.kt:61` and `SettingsScreen.kt:359` render `userStats.streak` as stored. The streak is recalculated only inside `awardXp` (`StudyViewModel.kt:315-330`, `nextStreak`), which runs only when the user earns XP.
- **Repro:** Earn a 10-day streak, skip 5 days, open the Dashboard. It still says 10 days. It resets to 1 on the next Good answer.
- **Fix:** Derive the display streak as `if (daysBetween(lastActivity, today) > 1) 0 else streak` in a pure, tested function.
- **Confidence:** High.

### F-10 — P2 — Android backup and device transfer include speech transcripts and roleplay conversations *(Prior #9: CONFIRMED, and deliberate)*
- **Evidence [Static]:** `AndroidManifest.xml:31` sets `allowBackup="true"`. `data_extraction_rules.xml` excludes only `datastore/settings.preferences_pb`, and its own comment says "everything else (the vocabulary database…) is fine to carry over". The single Room file holds `transcripts` (the user's recognised speech), `roleplay_messages`, `review_events`, `user_stats` and `activity_log`.
- **Assessment:** This is not a vulnerability; Android cloud backup is end-to-end encrypted when the device has a lock screen. It is a privacy-scope decision that has to be disclosed: transcripts are derived from the user's voice. Individual tables cannot be excluded, because it is one database file.
- **Options (product decision):** (a) keep it and disclose it in the privacy policy, or (b) move transcripts and roleplay into a second database file and exclude that file.
- **Confidence:** High.

### F-11 — P2 — No in-app privacy policy, and no way to delete the stored API key
- **Evidence [Static]:** The strings and screens contain no privacy-policy link (the only privacy text is `settings_tts_privacy_desc`). `PreferenceManager` has `saveApiKey` and no clear method, and "Wipe all progress" (`SettingsViewModel.kt:152-168`) leaves the key in place.
- **Impact:** Google Play's User Data policy requires a privacy policy both in the Console and inside the app for apps that handle personal or sensitive data. This app requests `RECORD_AUDIO` and sends user text to Groq. Please verify the current policy wording; I did not check it against live policy text. Users cannot revoke the credential without clearing app data.
- **Fix:** Add a privacy-policy link in Settings and a "Remove API key" action that deletes the encrypted entry, the legacy entry and, optionally, the Keystore alias.
- **Confidence:** High for the absence. The policy requirement should be confirmed.

### F-12 — P2 [Needs device] — The `openai/gpt-oss-120b` reasoning budget can starve replies; `finish_reason` is ignored
- **Evidence [Static]:** `max_completion_tokens` is 1024 for translation and word lookups (`GroqHelper.kt:204`, `:234`) and 512 for roleplay (`:365`, `:391`). `contentOf` (`:686-692`) reads `message.content` and ignores `finish_reason`. gpt-oss is a reasoning model. If the provider counts reasoning tokens against `max_completion_tokens`, which is my understanding but **not verified here**, long inputs can come back truncated or empty and surface as the generic "couldn't read the answer" failure.
- **Fix:** Set `reasoning_effort` low, if Groq supports it for this model. Detect `finish_reason == "length"` and show a specific message.
- **Verification:** Extend `GroqLiveTest` with a 3,500-character input and a long roleplay history, and assert `finish_reason`.
- **Confidence:** Medium. This is a hypothesis.

### F-13 — P3 — Daily notifications do not deep-link to their word *(Prior #12: CONFIRMED)*
- **Evidence [Static]:** `DailyWordNotification.kt:77-86` builds an explicit `MainActivity` intent with no extras. `MainActivity` reads no intent extras and does not override `onNewIntent`. The NavHost has no deep links. The widget click (`WordWidget.kt` `actionStartActivity<MainActivity>()`) does the same.
- **Fix:** Put the word id in an extra (an immutable PendingIntent with a per-id request code), handle it in `onCreate`/`onNewIntent`, and navigate to the Library detail. Validate that the id exists. The intent is internal and explicit, so no exported deep link is needed.

### F-14 — P3 — The daily-word slot drifts after DST or timezone changes until the next cold start *(Prior #5: PARTIALLY CONFIRMED)*
- **Evidence [Static]:** The 24 h periodic work runs on elapsed time. `rescheduleIfZoneChanged` re-anchors it correctly (`CANCEL_AND_REENQUEUE`, with good analysis in `DailyWordWorker.kt:66-86`), but it is called only from `MainApp.onCreate` (`MainApp.kt:47`). Nothing listens for `ACTION_TIMEZONE_CHANGED` or `ACTION_TIME_CHANGED`.
- **Impact:** After a DST transition the notification arrives at 08:00 or 10:00 until the process is next created. WorkManager's periodic scheduling is also inexact under Doze, so "09:00" is approximate in any case.
- **Fix (optional):** In `doWork`, check the offset and reschedule if it has changed. That self-heals after one firing without a manifest receiver.

### F-15 — P3 [Needs device] — TTS may use a network voice *(Prior #6: PARTIALLY CONFIRMED / REQUIRES DEVICE VERIFICATION)*
- **Evidence [Static]:** `TTSHelper.kt:153-164` selects the first German voice where `!isNetworkConnectionRequired`. If none exists, the engine default from `setLanguage(Locale.GERMAN)` stays in effect, and that may be a network voice. Nothing passes `KEY_FEATURE_NETWORK_SYNTHESIS=false`. The selection also ignores the user's dialect (de-AT/de-CH) and may pick a de-CH voice for a de-DE user. The Settings copy ("Prefers on-device voices") is accurate.
- **Fix:** If no offline voice exists, say so, or pass the engine-specific flag. Pick the voice matching `selectedDialect`, falling back to de-DE.

### F-16 — P3 — API-key input is cleared before the save is known to have succeeded *(Prior #7: CONFIRMED, low impact)*
- **Evidence [Static]:** `SettingsScreen.kt:184-185` and `:200-201` call `viewModel.saveApiKey(apiKeyInput); apiKeyInput = ""` synchronously, while the save is asynchronous (`SettingsViewModel.kt:110-123`). On a Keystore failure the banner says "not saved" (honest), but the user has to type the key again. `remember(hasApiKey)` (`:53`) also resets the field.
- **Fix:** Expose a save result and clear the field only on success.

### F-17 — P3 — Hardcoded English UI strings *(Prior #11: CONFIRMED)*
- `RoleplayScenario.kt`: scenario `title` and `context` are English literals, shown in the roleplay header and picker (`RoleplayScreen.kt` header and dropdown).
- `SettingsScreen.kt:67-71`: the CEFR labels "A1 (Beginner)" and so on.
- `AndroidManifest.xml:55`: widget receiver label "DeutschFlow Word".
- `tools/audit_repo.py` checks parity between `values` and `values-de` only, so it cannot catch these.
- The `RoleplayViewModel.kt:317-320` comment claims the header is localised. It is not.
- Note: scenario *context* is also sent to the model as English instructions. Keep the model-facing text separate from the UI text.

### F-18 — P3 — Transcript grammar state persists between recordings *(Prior #10: PARTIALLY CONFIRMED)*
- **Evidence [Static]:** `TranscriptViewModel.startListening` (`:238-241`) and the failure branch (`:303-310`) clear translation, keywords and example but **not** `_grammarNotes`.
- **Not user-visible today:** the UI renders grammar only when `translation.isNotEmpty()` (`TranscriptScreen.kt:332-336`), and every success overwrites `_grammarNotes`. This is a latent bug that the next UI change could expose.
- **Fix:** Clear `_grammarNotes` alongside the other fields.
- **Test:** After a success, start a new recording and assert `grammarNotes` is empty.

### F-19 — P3 — Roleplay scenario switching: the UI guards it, the ViewModel does not, and utterances can be dropped *(Prior #4: PARTIALLY CONFIRMED)*
- **Evidence [Static]:** The picker and restart controls are disabled while `isProcessing` (`RoleplayScreen.kt:104`, `:169`), which closes the original mixing path. The ViewModel itself has no generation token: `startSession` neither cancels the in-flight job nor marks it stale, and a stale reply would be appended and persisted into the new scene.
- **Remaining reachable path:** start listening (allowed, because `isProcessing` is false), open the picker and choose a scenario. The opening turn sets `isProcessing`. The recognizer then delivers the user's sentence, and `sendInput` returns early (`RoleplayViewModel.kt:249`). The utterance is dropped silently, and the recognizer is not cancelled on the scenario change.
- **Fix:** Use a session token checked before appending or persisting. Cancel the recognizer in `startSession`. Disable the picker while listening.

### F-20 — P3 — HARD earns no XP and does not keep the streak
- `StudyViewModel.kt:193` awards XP only for `quality >= GOOD`. `SRSEngine` explicitly treats HARD as a success. A user who honestly presses Hard all day ends it with no streak. That contradicts the engine's stated intent (`SRSEngine.kt:38-47`). This is a product decision; I recommend awarding XP for HARD.

### F-21 — P3 — Due times are not aligned to the day
- `SRSEngine.kt:94-95` sets `nextReview = now + N days` exactly. A card answered at 22:00 with a 1-day interval is not due at 09:00 the next day. Consider aligning to the start of the local day (as Anki does). Note that `review_events.actualDays` uses 24 h floors (`elapsedReviewDays`) while the streak uses calendar days, which is consistent within each metric.

### F-22 — P3 — Performance hotspots (measurable, not speculative)
- `DailyWord.today()` (`DailyWord.kt:23-26`) loads the **entire** library to pick one row, on every widget redraw. `WidgetUpdater.refresh()` runs after every library write. Use `COUNT(*)` plus `ORDER BY id LIMIT 1 OFFSET :k`.
- `StudyViewModel.startSession` reads both the due list and the full library even when the due list is non-empty (`:115-118`).
- `DashboardViewModel.masteryStats` maps the full library on every vocabulary change. It could be one aggregate `SELECT SUM(CASE …)`.
- `PracticeViewModel.loadRandomTarget` loads the whole library.
- `MainActivity` injects `TTSHelper` (`@Singleton`, `init { initialize() }`), so the TTS service is bound on **every cold start**, even when nothing speaks. Make it lazy (`dagger.Lazy<TTSHelper>`).
- **To measure:** Macrobenchmark cold start with and without the TTS binding, and a widget redraw at 5,000 words.

### F-23 — P3 — The widget shows yesterday's word between midnight and about 09:00
- `DailyWord` picks by `LocalDate.now()`, but the widget redraws only on a library write, from the 09:00 worker, or on `updatePeriodMillis` (24 h, unaligned). Accept and document it, or schedule a midnight refresh.

### F-24 — P3 — The model's `word` field becomes the saved key
- `saveWordDetails` stores `details.word` (`TranscriptViewModel.kt:427`), not the chip the user tapped. The model may return a lemma ("gehen" for "ging") or a different word, and saving then merges into whatever entry owns that key. The sheet shows the word before saving, which mitigates this. Consider showing "saved as *X*" when it differs, or keying on the tapped token.

### F-25 — P3 [Needs device] — Accessibility items
- Several `IconButton`s are sized below 48 dp: `Modifier.size(36.dp)` at `TranscriptScreen.kt:693`, `:707` and `RoleplayScreen.kt` (restart and speak buttons), and the banner close button at `SettingsScreen.kt:100` (24 dp). Whether `minimumInteractiveComponentSize` still expands the touch target with an explicit outer `size()` needs the Accessibility Scanner on a device.
- The four SRS buttons use `labelSmall` with `maxLines = 1` in one row (`StudyScreen.kt:487-492`). At 200 % font scale "Again", "Hard", "Good" and "Easy" will clip, the German labels in particular.
- The flashcard is a single clickable surface (`onClickLabel` is provided, which is good). Confirm TalkBack reads the back face after a flip, because the content is swapped by rotation.
- **Positives:** an error-banner live region with a test (`ErrorBannerAnnouncementTest`), reduced-motion support (`LocalReducedMotion`), the final transcript announced, radio semantics on Settings rows, and nav labels dropped above 1.3× font scale with content descriptions kept.

### F-26 — Info — Local build environment unhealthy (not an app defect)
- The repo root and `app/` contain 9 `hs_err_pid*.log` and `replay_pid*.log` files (about 5 MB). All are native-memory-exhaustion crashes of Gradle JVMs ("insufficient memory… malloc failed / Failed to commit metaspace"). ### D.2 Existing protections (verified)

The legacy plaintext entry is migrated and removed. Decryption failure shows as `Unreadable`, not a crash. |

| Exported components | `MainActivity` (launcher, required) and `WordWidgetReceiver` (exported, as app widgets must be; an `APPWIDGET_UPDATE` from another app only forces a redraw). There are no providers, no services, and no deep-link filters. |
| PendingIntent | Explicit component with `FLAG_IMMUTABLE` (`DailyWordNotification.kt:81-85`). |

| Error disclosure | Provider error messages are shown verbatim. That is acceptable: they concern the user's own key. Stack traces are not shown. |
| CI supply chain | Actions pinned by SHA, `permissions: contents: read`, Dependabot for gradle, npm and actions. |

### D.3 Data that leaves the device
| Data | Destination | Trigger |
|---|---|---|
| Recognised German text (≤4,000 chars), CEFR level | Groq (`api.groq.com`) under the **user's own key** | Every completed transcript utterance (automatic after recording) |
| Single tapped word | Groq | Tapping a keyword chip |
| Roleplay turns (last 12, ≤4,000 chars total), English scenario text, CEFR level | Groq | Each roleplay turn and opening |

### D.4 Retention and deletion
- "Wipe all progress" deletes all six tables in one transaction. The API key, dialect, CEFR level and auto-play setting are kept (F-11).
- The roleplay table keeps only the current conversation and is cleared on a new scenario. Transcripts are kept indefinitely until deleted.
- `review_events` rows for deleted words are kept forever (F-03).

### D.5 Google Play Data Safety implications (for the owner to decide; not legal advice)
- **Audio:** recorded but not collected or transmitted, because recognition is on-device.
- **User-generated content and messages:** speech-derived text and roleplay text are transmitted off-device to a third party (Groq). This is likely reportable as collected and/or shared, even though the user supplies the key.
- **App activity / in-app actions** (review history, XP): on-device only, apart from Android backup.
- Encryption in transit: yes. A deletion mechanism exists for learning data, but not for the API key.
- A privacy policy URL is required in the Console and in the app (F-11).
