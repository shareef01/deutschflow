## A-01 · P1 · Backup export and import run entirely on the main thread [Static]

`SettingsViewModel.exportBackup` and `importBackup` (`ui/viewmodel/SettingsViewModel.kt:219`
and `:227`) hand off to `launchGuarded`, which is `viewModelScope.launch`
(`ui/viewmodel/LaunchGuarded.kt:33`) — `viewModelScope` dispatches on
`Dispatchers.Main.immediate`. Nothing below that point ever switches dispatcher:
`git grep Dispatchers app/src/main/java/com/aus/deutschflow/data/local/backup/` returns
nothing, and `BackupManager.exportToStream`/`importFromStream`
(`data/local/backup/BackupManager.kt:158`, `:163`) are plain wrappers around blocking
work.

So the UI thread does all of:

- `readBoundedBytes` — a blocking read of up to 70 MB, with a naive `containsBytes`
  scan (`BackupManager.kt:525`) that is O(file × marker) over those 70 MB.
- `BackupCrypto.decrypt` — PBKDF2-HMAC-SHA256 at 210 000 iterations
  (`BackupCrypto.kt:29`), then AES-GCM over the whole payload.
- `JSONObject(content)` plus the whole of `validateBackupJson` (`BackupManager.kt:610`).
- On export: building the entire library as JSON and `toString(2)` on it.

On a mid-range phone that is several hundred milliseconds at best and comfortably past
the 5-second input-dispatch ANR threshold for a large library — on the two actions where
the user has just picked a file and expects a spinner, and where the app shows nothing
until the call returns. The regression is invisible to the test suite:
`BackupManagerIntegrationTest` and `BackupStreamReadTest` drive `BackupManager` directly
with their own streams, so no test observes the thread the production path uses.

**Fix:** wrap the bodies of `exportToStream` and `importFromStream` in
`withContext(Dispatchers.IO)`. `Room`'s `withTransaction` already hops off the main
thread, but the read and the KDF above it do not.

**Do not fix this without reading A-01b.**

### A-01b · P1 · …and the SAF stream is closed under the reader the moment that changes

`ui/screens/SettingsScreen.kt:105` and `:704` open the document with `use { }` and pass
the live stream into a fire-and-forget ViewModel call:

```kotlin
context.contentResolver.openInputStream(uri)?.use { stream ->
    viewModel.importBackup(inputStream = stream, passphrase = null, …)
}
```

`importBackup` is not `suspend`; it launches and returns, and the `use` block then closes
the stream. This works today *only* because `Main.immediate` runs the coroutine body
inline, so `readBackupText` consumes the stream before `use` closes it. The fix for A-01
is exactly what breaks this: the first `withContext(Dispatchers.IO)` suspends, `use`
returns and closes the stream, and every import fails.

**Fix:** read the bytes where the stream is opened (or hoist the `use` into the
ViewModel), then process off the main thread. `SettingsScreen.kt:649` (export) has the
same shape and the same coupling.

## A-02 · P2 · The AI client has no retry, and the remediation doc says it does [Static]

`GroqHelper.postTo` (`service/GroqHelper.kt:541`) makes one attempt: 30-second connect
and read timeouts, no retry loop, no backoff, no distinction between a retryable 5xx /
transient network failure and a provider rejection. `git grep -i "retry|backoff"` over
`app/src/main` finds only comments and the roleplay UI's manual *Retry* button.

The web client does all of it — `web/src/lib/ai/groq.ts:77` (`RETRY_BACKOFF_MS = [300,
600]`), `:266` (retryable 500/502/503/504), `:279` (fail fast on 400/401/403/404/429),
`:294` (retry transient network errors).

`AUDIT_REMEDIATION.md:23` records **P9-AI-RESILIENCE — "Web & Android — AI model
configuration centralization, bounded retries, error classification" — FIXED AND
VERIFIED**, citing only Vitest files. The Android half of that row is not true, and the
cross-platform contract test does not pin retry behaviour (`CrossPlatformContractTest.kt`
has no retry assertions), which is why the drift went unnoticed.

**Impact:** one dropped connection, one 503, or one free-tier 429 becomes
"Translation failed" for the user, and the request that did reach the provider is spent
either way. The README's stated design is that the clients "share behaviour, not code";
this is behaviour they do not share.

**Fix:** port `MAX_POST_RETRIES` + `isRetryableStatus` + backoff into `postTo`, honouring
cooperative cancellation (the existing `ensureActive()` in the catch already supports
it), and add the retry policy to the contract fixture.

## A-03 · P2 · "1 cards reviewed" [Run]

`lintDebug`'s three `PluralsCandidate` warnings are 2 false positives (`ai_input_too_long`
and `ai_message_too_long` can never be 1) and one real one:

- `app/src/main/res/values/strings.xml:126` — `<string name="study_reviewed_stat">%1$d cards reviewed</string>`
- `app/src/main/res/values-de/strings.xml:132` — `%1$d Karten wiederholt`

It is reachable with a count of 1: `ui/screens/StudyScreen.kt:191` computes
`reviewedTotal`, `:235` renders the block for `reviewedTotal > 0`, and `:243` formats it.
A one-card session — or an extra-practice restart on a one-word library — shows
"1 cards reviewed" / "1 Karten wiederholt".

Every other count in the app is a proper `<plurals>` (six of them, EN and DE:
`history_word_count`, `study_remaining`, `dashboard_due_banner`, `dashboard_words_total`,
`dashboard_streak`, `settings_stat_streak_days`), so this is a slip rather than a missing
pattern. **Fix:** convert to `<plurals>` with `one`/`other` in both locales and use
`pluralStringResource`.

## A-04 · P2 · No crash reporting anywhere, by design and by omission [Static]

`gradle/libs.versions.toml` carries no crash/telemetry SDK, and `LaunchGuarded.kt:18`
says so in passing: *"a disk-full or corrupted-database error while saving a word took the
whole app down, in a project with no crash reporting to notice it had happened."*
`launchGuarded` was added to stop those reaching the default handler — and every one of
them now goes to `Log.w` only. `MainApp.kt:32`'s process scope does the same.

The consequence for a release is that whole classes of failure are unobservable in the
field: Keystore refusals (`PreferenceManager.saveApiKey` returning false), failed backup
imports, `Room` IO errors, and the ANR that A-01 will produce on large libraries. There
is also no way to answer "how many users hit the speech recogniser's
`ERROR_LANGUAGE_UNAVAILABLE`".

**Recommendation:** add Play Console's own ANR/crash reporting path (it needs no SDK) and
a minimal `Thread.setDefaultUncaughtExceptionHandler` → same sink, plus an opt-in note in
`SECURITY.md`/the store listing. Content logging must stay forbidden — the R8
`-assumenosideeffects` block and the `SpeechRecognizerHelper` comments show that rule is
deliberate, and a crash reporter with automatic breadcrumbs would quietly break it.

## A-05 · P3 · Transcripts are copied to the clipboard unmarked [Static]

`ui/components/TextFormatting.kt:29-31`:

```kotlin
fun copyToClipboard(context: Context, text: String) {
    clipboard.setPrimaryClip(ClipData.newPlainText(TRANSCRIPT_CLIP_LABEL, text))
}
```

A transcript is the user's own speech, and this app goes to real lengths to keep it off
disk elsewhere: `proguard-rules.pro` strips debug logging so a careless `Log.d` cannot
leak speech, `SpeechRecognizerHelper` never logs recognition content, and
`data_extraction_rules.xml` excludes the database from cloud backup and device transfer.
The clipboard is the one remaining channel, and the clip is not marked
`ClipDescription.EXTRA_IS_SENSITIVE`, so the overdrawn clipboard preview and any
keyboard's clipboard history treat the sentence as ordinary text. **Fix:** one line
setting the extra on the `ClipDescription`, for the same reason the rest of the app is
careful.

## A-06 · P3 · One user-visible string is outside the resource system [Static]

`TextFormatting.kt:28`: `const val TRANSCRIPT_CLIP_LABEL = "German Transcript"`. That
label is rendered in the system paste sheet, so a German user sees English there, and no
translation can reach it. `tools/audit_repo.py` passes because it compares the keys the
resource files declare — a literal in Kotlin is invisible to it, the same gap
`AUDIT_2026-10-22.md` records for the web's JSX text nodes (R-02, X-02).

**Fix:** take the label from a string resource at the call site, and consider teaching
`audit_repo.py` to flag string literals passed to `ClipData.newPlainText` and
`contentDescription`-adjacent UI parameters.

## A-07 · P3 · Dates follow the device locale, not the app's language [Static]

`TextFormatting.kt:37` — `rememberDateFormat` builds `SimpleDateFormat(pattern,
Locale.getDefault())`. With `localeConfig` (`res/xml/locales_config.xml`) the app declares
per-app language support for `en` and `de`, but Android's per-app locale updates the
process `Configuration`, not `Locale.getDefault()` — which keeps reporting the *system*
locale. A German speaker on an English phone therefore gets a German UI with English
month and day names in the History rows.

**Fix:** build the format from `LocalConfiguration.current.locales[0]`, which is the
app's locale.

## A-08 · P3 · Dependabot ignores exactly the versions lint reports, permanently [Run]

`lintDebug` reports 10 `GradleDependency` warnings — `room` 2.8.5, `compose-bom`
2026.09.00, `navigation-compose` 2.10.2, `work-runtime-ktx` 2.12.0, `core-ktx` 1.19.1,
`ksp` 2.3.12, `glance-appwidget` 1.2.0, plus three more `room` artifacts — and
`.github/dependabot.yml` has an `ignore` entry for every one of them except Glance,
reasoned as *"versions of the first batch of group PRs (closed unmerged in October
2026)"*.

The entries have no expiry, so the automation can never re-propose those versions, while
`lintDebug` — which CI runs — reports them on every build. The two mechanisms now
disagree by construction, which is how a warnings list stops being read. Either drop the
`ignore` entries and take the bumps as a group, or record in the file why each one is
held and when it expires. The Glance omission suggests the list is already drifting from
its own rationale.

## A-10 · P4 · Cold start pays for a notification nobody asked for, and is unmeasured [Static]

`MainApp.kt:41` calls `DailyWordWorker.schedule(this)` from `Application.onCreate` on
every launch, which is the first touch of `WorkManager` — one of the more expensive
AndroidX initializers — plus two further `appScope.launch` calls (`:47`, `:67`) for the
timezone re-anchor and the legacy-key migration. None of the three is conditional on
anything the user has enabled, and all three happen before the first frame.

There is no `androidx.profileinstaller`, no `:baselineprofile` or `:macrobenchmark`
module (`settings.gradle.kts` includes `:app` only), and `PERFORMANCE_AUDIT.md` predates
the current startup path, so none of this is measured either way.

**Recommendation:** measure before changing anything — a `:macrobenchmark` module with a
startup test would also let the Compose work that `PERFORMANCE_AUDIT.md` reasoned about
from first principles be checked. Then consider `Configuration.Provider` + lazy
`WorkManager` init gated on notifications actually being enabled, and a baseline profile,
which is the cheapest real win for a Compose app of this size.

## Verified sound

Recorded so the next audit does not redo it. Each of these was read closely and is in
good order.

- **API key storage.** `KeystoreCipher` — AES-256-GCM, `setRandomizedEncryptionRequired`,
  IV prefixed rather than stored separately, not lock-screen-bound on purpose (documented
  reason: translation can run with the screen off), `@Synchronized` key generation
  against the check-then-generate race, and `null`-not-plaintext on every failure path.
  `PreferenceManager.saveApiKey` refuses to fall back to plaintext and reports the
  failure to the user; `migrateLegacyApiKey` is atomic and re-runs on every launch.
- **Backup envelope.** PBKDF2-HMAC-SHA256 + AES-256-GCM with version, KDF and
  iteration-count allow-lists (50 000..1 000 000), salt/IV size checks, ciphertext and
  plaintext caps enforced before allocation, strict UTF-8 (no U+FFFD substitution),
  `AEADBadTagException` mapped to "wrong passphrase", and a validator that runs on the
  app's own export before it is written. The passphrase is never persisted.
  *Minor:* the write side uses 210 000 iterations where current OWASP PBKDF2-SHA256
  guidance is ~600 000; raising it is backward-compatible because the read side already
  accepts up to 1 000 000.
- **Migrations.** 2 → 18 all present and in order, with debug-only
  `fallbackToDestructiveMigration`. `MIGRATION_16_17`'s "this migration can only split,
  never merge" argument is correct (the new key is strictly finer than the old one, so no
  new collision is possible and the unique index can stay up), and historical folds are
  frozen (`legacyGermanKey`) rather than tracking the live `germanKey`. Merges move
  `review_events` onto the survivor before deleting the loser.
- **Manifest and IPC.** Least permissions, `hardware.microphone` explicitly not required,
  every PendingIntent explicit + `FLAG_IMMUTABLE`, `dataExtractionRules` excludes both
  the database and the settings DataStore, no cleartext, no exported component beyond the
  launcher and the widget receiver (which is required to be exported; its unprotected
  `APPWIDGET_UPDATE` is nuisance-only).
- **Speech and TTS lifecycle.** Generation counters reject stale `RecognitionListener`
  callbacks; the `UtteranceDeliveryBus` gives exactly-once, in-order delivery through a
  single drainer instead of dropping utterances on a contended buffer; transient audio
  focus is requested and abandoned per phrase; `OnLeavingScreen` releases the mic on both
  `ON_STOP` and disposal, because the back-stack entry is saved rather than destroyed;
  `TTSHelper` reads state and acts under one lock and rebuilds an engine that failed.
- **Coroutines.** No `GlobalScope`, no `runBlocking`, no `Thread.sleep`. Every write goes
  through `launchGuarded` with `CancellationException` rethrown; `GroqHelper.postTo`
  aborts the socket from a child coroutine rather than `invokeOnCompletion` (which cannot
  fire on a blocked job).
- **Accessibility.** Every icon-only control carries a `contentDescription` from
  resources; the 30-odd `contentDescription = null` are decorative icons beside a visible
  label, which is correct. `collectAsStateWithLifecycle` is used everywhere (no
  `collectAsState`), all three `LazyColumn`s have stable keys, and the navigation bar
  drops its labels to icons alone past 1.3× font scale rather than let Material clip them.
- **SRS.** SM-2 with an ease floor and a documented ceiling, calendar-day due dates
  (`dueAt`) so an evening review is not due at 22:00 the next day, `Hard` distinguished
  from `Again`, and an extra-practice path that never pushes a card further away.
- **Room surface.** No `allowMainThreadQueries`, no string-built SQL, indices on every
  ordered/filtered column the screens read, and a `save()`/`restore()` that resolve
  uniqueness inside a transaction and keep review history attached across merges and undo.

## Test and CI gaps

- **The connected suite is not hermetic, and the AI path is therefore untested by CI.**
  `GroqLiveTest` and `GroqModelAvailabilityTest` call `api.groq.com` with the device's
  stored key and self-skip when there is none (`GroqLiveTest.kt:24`, `:47`) — which is
  also exactly what happens on the emulator jobs. So the one behaviour A-02 is about has
  no automated coverage in either direction.
- **No test observes the thread the backup path runs on** (A-01), and none can, until the
  dispatcher is injected or the work is moved. Worth adding: a test that asserts
  `importFromStream` does not run on `Dispatchers.Main`.
- **Instrumented coverage is the right shape but harness-only:** migrations, DAO
  contracts, recogniser seams, the platform contract at API 31/35/36. What is missing is
  anything UI-level beyond two Compose tests (`ErrorBannerAnnouncementTest`,
  `GlassButtonFontScaleTest`) and `OpenWordFromOutsideTest`. The web client has Playwright
  accessibility tests; Android has none.

## What I did not verify

- Instrumented tests, the release build and R8's actual output — no emulator, and
  `assembleRelease` was not run, so the shrinker's treatment of the new `review_events`
  and roleplay paths is unconfirmed beyond the rules being present.
- Startup, frame timing and ANR behaviour: A-01 and A-10 are read from the code, not
  measured. A-01 in particular would be settled in ten minutes on a device with a 20 MB
  library.
- The web client was out of scope; it was read only to check the A-02 parity claim.

## Recommended order

1. **A-01 + A-01b together** — one change, off the main thread, stream lifetime fixed in
   the same commit. Everything else in this report is smaller than an ANR on the screen
   where users move their data between devices.
2. **A-04** — you cannot see A-01, A-02 or anything else in the field without it.
3. **A-02** — restores a behaviour the docs already claim, and the contract test that
   would have caught it.
4. **A-03, A-05, A-06, A-07** — small, self-contained, user-visible.
5. **A-08, A-09** — hygiene, so the lint report stays worth reading.
6. **A-10** — measure first, then change.
