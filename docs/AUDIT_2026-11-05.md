## B-01 — P1 — Failed conversation reads can delete the saved conversation

**Evidence: reproduced repository behavior; statically traced hook sequence.**

`web/src/lib/db/repository.ts:727–732` converts every `loadConversation` failure into `[]`. `web/src/hooks/useRoleplay.ts:264–277` accepts that as a successful restore. `openScenarioIfEmpty` at line 291 then treats it as no saved conversation, and `startSession` at line 240 clears the conversation table before requesting an opening.

A transient read failure followed by working writes therefore deletes the conversation the read could not see. This is data loss, not merely a missing chat until reload. The mounted hidden RoleplayMode also invokes this sequence (B-04), so it does not require the user to deliberately restart a scene.

Probe: seed one saved message, fail the next `orderBy(...).toArray()` once, call the real `loadConversation`, observe `[]`, then execute the hook's clear/new-opening sequence. The saved message disappears and only the new opening remains.

**Fix:** propagate restore failure or return an explicit failure result. Keep the saved table untouched and show a retry action. Starting a fresh conversation must be a deliberate successful operation, not the fallback for a failed read. Android already distinguishes `restoreFailed` in RoleplayViewModel.

## B-02 — P2 — A stale vocabulary edit can undo a committed review schedule

**Evidence: reproduced on web; analogous Android write path identified statically.**

`web/src/lib/db/repository.ts:250–253` prefers the edit input's schedule over the database row re-read inside its transaction. The edit caller spreads an entire VocabularyEntry (`web/src/app/(app)/vocabulary/page.tsx:166`). An edit submitted from an older snapshot can therefore undo a review committed concurrently, including one from another tab.

Probe: save a new card, retain its edit snapshot, commit Good through the real `recordReview` (reviewCount becomes 1), then call `saveVocabulary` with the retained snapshot and a corrected translation. The translation saves, but reviewCount and nextReview both revert to 0. The review event remains, so the schedule and recorded history disagree.

Android's `VocabularyDao.save` likewise writes the full caller entity on the same-ID path (`app/src/main/java/com/aus/deutschflow/data/local/dao/VocabularyDao.kt:227`), rather than preserving the fresh schedule. Android's single visible screen reduces the race surface, but overlapping review/import/edit writes remain unprotected by this API.

**Fix:** separate content edits from schedule writes. Within the edit transaction, preserve the stored schedule/identity and update only editable content, or reject a stale edit explicitly. Apply the same rule to renames and merge decisions.

## B-03 — P2 — Pending microphone permission can reopen recognition after screen cleanup

**Evidence: reproduced for all three web hooks with controlled permission resolution.**

The web Transcript, Repetition and Roleplay startup callbacks await microphone permission and the stored dialect, then unconditionally call `recognizer.startListening`:

- `web/src/hooks/useTranscript.ts:221–227`
- `web/src/hooks/usePractice.ts:158–164`
- `web/src/hooks/useRoleplay.ts:330–336`

Their cleanup paths cancel the current singleton recognizer, but do not invalidate the pending startup. If a learner leaves the screen or switches Practice modes before permission resolves, granting permission later starts recognition for the departed screen. Since the recognizer is shared, the resulting utterance can reach the newly active mode's listener.

Probe for each hook: begin startup with permission unresolved, run effect cleanup/cancel, then resolve permission true. In every case the recognizer's start method is called after cancellation.

**Fix:** give startup an ownership generation/abort token invalidated on unmount, cancellation and mode deactivation. Recheck ownership and active state after every await before acquiring the recognizer. A ref that only blocks duplicate starts does not cancel an accepted start.

## B-04 — P2 — Hidden web roleplay opens a scene while Repetition is selected

**Evidence: inactive-hook opening reproduced; hidden-component wiring verified statically.**

`web/src/app/(app)/practice/page.tsx:51–57` mounts RoleplayMode even while its panel is hidden. Its mount effect at line 254 unconditionally calls `openScenarioIfEmpty()`. The hook's `active` flag gates speech subscriptions and cancels an existing request when it becomes inactive, but does not gate `openScenarioIfEmpty`, `startSession`, or `runOpening`.

With no saved conversation and a configured key, opening Practice on its default Repetition tab therefore clears/opens a roleplay scene, issues an AI request, persists the greeting, and can speak it with autoplay enabled. Hiding a panel does not stop its effects. The initial inactive cancellation runs before the asynchronous restore starts the new opening request.

Probe: instantiate `useRoleplay({ active: false })`, run its mount effects, and execute the same opening call used by RoleplayMode. The stub AI opening method is called once despite the inactive flag.

**Fix:** start/resume the opening only when Roleplay becomes active; pass active state to the component/effect or enforce it in the hook. Preserve the existing conversation across mode changes.

## B-05 — P2 — Android roleplay can begin speaking after the learner leaves

**Evidence: static lifecycle trace; not device-reproduced in this pass.**

`app/src/main/java/com/aus/deutschflow/ui/screens/RoleplayScreen.kt:117–121` stops microphone capture and current TTS on departure/backgrounding. `RoleplayViewModel.cancelListening` at line 290 only cancels the microphone startup/recognizer; it does not cancel or invalidate `turnJob`.

The ViewModel survives tab switches in the saved navigation back stack. A pending opening or reply can finish afterward and call `ttsHelper.speak` at `RoleplayViewModel.kt:352` or `:400` when autoplay is enabled. The prior `stopSpeaking()` only stops playback at that instant. TTSHelper.speak has no foreground ownership guard, so the completed request can initiate new playback over another screen or in the background.

**Fix:** explicitly invalidate/cancel abandoned roleplay work when the screen leaves, or retain the reply but gate autoplay on foreground ownership, checking again after the preference read. Preserve a recoverable retry path if the request is cancelled.

## Recommended order

1. B-01: stop read failure from triggering destructive conversation replacement.
2. B-02: protect review schedules from content-edit snapshots.
3. B-03: invalidate pending microphone startup on loss of ownership.
4. B-04/B-05: gate roleplay requests and autoplay on the visible/foreground owner.

The two backup issues fixed in `696137f` are not reopened by these findings. The existing `docs/AUDIT_2026-11-02.md` was left untouched. Dependency freshness warnings and other already-recorded hygiene items were not promoted into new findings.


## Remediation and verification — 5 November 2026

All five source findings above are addressed by this remediation. The findings describe baseline commit `696137f`; their source line numbers refer to that baseline.

- **B-01:** Conversation reads propagate errors. Roleplay restores only when active, blocks scene replacement on a failed restore, displays the existing storage-error message, and retries the read through Retry. A failed clear also leaves the visible conversation intact.
- **B-02:** Web and Android content edits use the freshly stored schedule rather than schedule fields from the UI snapshot, including renames. Tests commit a newer review schedule before submitting the older edit.
- **B-03:** A shared web microphone-start hook owns pending permission/settings reads. Cleanup, explicit cancellation and mode deactivation invalidate the attempt; ownership is checked after both awaits. Browser regressions verify late permission cannot start recording and that a fresh attempt still works after returning.
- **B-04:** Automatic roleplay opening is activation-scoped. Requests and playback check foreground ownership; stale request finalizers cannot unlock a replacement request.
- **B-05:** Android screen departure cancels and invalidates pending roleplay replies and pending scene openings, stops playback and clears queued speech. An interrupted user turn remains available through Retry; the device regression verifies recovery.
